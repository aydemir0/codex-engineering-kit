# v0.2 Release Evidence and Compatibility Design

Status: approved design direction, pre-implementation.

This document narrows Plan F from `docs/superpowers/plans/2026-09-03-codex-engineering-kit-v0.2-master.md` into an evidence-first release/compatibility design. It does not replace `docs/superpowers/specs/2026-09-03-codex-native-plugin-v0.2-final-design-v2.md`; where this document is silent, the final design remains authoritative.

## 1. Purpose

Plan F converts the implemented v0.2 feature set into a release surface whose public claims are traceable to current official platform documentation, reproducible acceptance evidence, deterministic repository tests, or an explicit limitation.

The chosen approach is staged and evidence-first:

1. establish a claim-to-evidence model;
2. run compatibility experiments independently on the declared Codex baselines;
3. preserve failures, blocked cases, and runtime differences instead of normalizing them into PASS;
4. update public documentation only after the corresponding evidence state is known;
5. close release readiness only when the release checklist points every promoted claim to evidence or a bounded limitation.

Plan F is not a documentation-only cleanup. Compatibility evidence is a release input, not supporting prose added after the fact.

## 3. Goals

Plan F must produce:

- a compatibility matrix for Codex CLI 0.147.0 and Desktop bundled runtime 0.152.0;
- a claim-to-evidence matrix for every material public v0.2 capability claim;
- a bounded RISK-001 experiment for explicit manifest hook configuration;
- separate recording of default hook discovery and explicit manifest override behavior;
- an interactive plugin-discovery acceptance record where the declared runtime exposes that surface;
- updated README, SECURITY, ROADMAP, and THIRD_PARTY_NOTICES content aligned with verified v0.2 behavior;
- an explicit v0.2 release-candidate checklist;
- deterministic release-contract tests that prevent stale or unsupported public claims from reappearing;
- fresh CI evidence on the release-documentation head before any Plan F closure claim.

## 4. Non-goals

Plan F does not:

- modify `main` or merge the feature branch;
- silently upgrade the declared 0.147.0/0.152.0 compatibility baselines;
- infer old-runtime support from current official documentation;
- treat current official documentation as proof that the declared old baselines implement the same contract;
- change the primary plugin manifest merely to make RISK-001 easier to close;
- execute or fabricate the 45-run context-efficiency campaign;
- promote `lean`, `feature parity`, `production-grade`, blanket `secure`, or unqualified `cross-platform` claims without their separate evidence gates;
- classify the Desktop parent-wait anomaly beyond what a reproducible targeted acceptance run proves;
- resolve semantic merge conflicts or modify unrelated architecture.

## 5. Evidence hierarchy

Plan F follows the final-design evidence hierarchy:

1. current official OpenAI documentation and first-party OpenAI source samples;
2. reproducible behavior on the declared local Codex versions;
3. repository tests and fresh CI evidence;
4. upstream/third-party engineering references;
5. model-generated research.

Current official documentation is a platform-contract source, not a retroactive compatibility result for Codex 0.147.0 or 0.152.0.

As of 2026-09-05, the official Codex Hooks documentation states that enabled plugins default to `hooks/hooks.json`, and that `.codex-plugin/plugin.json` may override the default using a `hooks` entry such as `"hooks": "./hooks/hooks.json"`. It also states that a manifest `hooks` entry replaces default `hooks/hooks.json` discovery for that plugin. The Plan F experiment must test that contract on both declared baseline runtimes rather than assuming parity from the current documentation alone.

Official source references used by this design:

- `https://developers.openai.com/codex/hooks`
- `https://developers.openai.com/codex/plugins`

## 6. Claim state model

Every material public claim has exactly one release state:

- `IMPLEMENTED` — repository implementation exists and deterministic contracts verify its static/behavioral boundary;
- `VERIFIED` — the relevant declared runtime or environment has reproducible acceptance evidence in addition to implementation evidence;
- `LIMITED` — implementation exists but a material limitation, runtime difference, or unresolved compatibility boundary prevents a broader claim;
- `PLANNED` — not implemented for the v0.2 release boundary.

`VERIFIED` is always scoped. A row must identify the runtime, operating system/environment where material, evidence reference, and limitations. A PASS on one baseline cannot promote the other baseline.

A claim matrix row contains at least:

- stable claim identifier;
- user-facing capability wording;
- release state;
- implementation evidence;
- runtime acceptance evidence when required;
- tested runtime/version scope;
- known limitation or open risk;
- public wording allowed by that evidence.

Missing evidence never defaults to success. Unsupported rows remain `LIMITED` or `PLANNED`.

## 7. Release evidence artifacts

Plan F should converge on three primary release documents:

- `docs/release/compatibility-matrix.md`
- `docs/release/claim-evidence-matrix.md`
- `docs/release/v0.2-rc-checklist.md`

Runtime-specific acceptance remains under `docs/research/evidence/` and is linked from those release documents. Raw or detailed local captures remain sanitized according to the existing repository policy; no auth token, session identifier, private transcript, machine-local cache root, or unbounded raw output is committed.

The release documents summarize evidence. They are not substitutes for the underlying executable or runtime records.

## 8. Compatibility matrix design

The compatibility matrix has separate columns or rows for:

- Codex CLI 0.147.0;
- Codex Desktop bundled runtime 0.152.0.

Each tested surface uses one of these result states:

- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT_RUN`

No generic `compatible` status is derived unless every capability required for that public compatibility statement is PASS on the stated runtime.

The matrix must cover at least:

- plugin manifest validation/discovery;
- repo-local marketplace install/list behavior where the runtime exposes it;
- bundled skill discovery;
- default plugin hook discovery through `hooks/hooks.json`;
- explicit manifest `hooks` override experiment;
- shipped hook lifecycle coverage relevant to the v0.2 claim;
- safe destructive-deny fixture and normal allow behavior;
- native reviewer/subagent loading and lifecycle evidence;
- compaction/state restore boundary;
- SessionEnd observed behavior and timeout limitation;
- interactive plugin discovery where available;
- any Desktop-specific parent/child wait behavior observed during targeted subagent acceptance.

Worktree CI acceptance remains Plan E evidence. A Codex-managed Desktop worktree claim is promoted only if separately observed on the Desktop runtime; manual Git-worktree acceptance must not be mislabeled as proof of Codex-managed worktree behavior.

## 9. RISK-001 explicit manifest hooks experiment

RISK-001 must be tested without mutating the primary `.codex-plugin/plugin.json` on the feature branch.

For each declared baseline runtime, the experiment uses a disposable plugin copy and disposable `CODEX_HOME` or equivalent isolated acceptance state. The fixture starts from the real plugin tree, then modifies only the disposable manifest to add:

```json
"hooks": "./hooks/hooks.json"
```

The experiment has two phases per runtime:

1. control: default hook discovery with the shipped primary manifest;
2. variant: explicit manifest hook override in the disposable plugin copy.

Both phases must exercise a real bounded hook event, not only parse or list the manifest. The recorded result includes exact runtime version, binary identity where already part of repository evidence policy, event observed, exit/process result, bounded hook evidence, and sanitized capture hash where applicable.

The experiment must not use a destructive payload. Existing safe acceptance sentinels remain the only destructive-deny fixture path.

If one baseline passes and the other fails or is blocked, RISK-001 remains open and the shipped primary manifest continues to rely on default `hooks/hooks.json` discovery. RISK-001 closes only when both declared baseline runtimes produce reproducible PASS evidence for the explicit override path.

One-off trust bypass may be used only when the acceptance harness has independently vetted the disposable hook source and records that bypass was used. Such a run proves hook loading/execution, not the normal interactive trust-review UX.

## 10. RISK-002 runtime skew handling

RISK-002 is not closed by a table with two version numbers. It is bounded through per-capability evidence.

Rules:

- never copy a 0.147.0 result into the 0.152.0 column or vice versa;
- record behavioral differences explicitly;
- a non-critical difference may ship as a documented limitation;
- a failure in a capability required by the release's public core claim blocks that claim or blocks the RC, depending on scope;
- newer Codex versions discovered during Plan F do not replace either declared baseline unless a separate design decision changes the release window.

The release may state a tested-against window only to the extent that the compatibility matrix supports the exact wording used.

## 11. SessionEnd discrepancy policy

The existing Codex CLI 0.147.0 SessionEnd discrepancy remains an explicit limitation until separately resolved by reproducible evidence.

Plan F must not change hook behavior or timeout configuration merely to make the discrepancy disappear from the release record. Compatibility evidence should distinguish:

- configured timeout contract;
- observed wall-clock behavior;
- whether the hook completed and persisted bounded state;
- whether the process/runtime enforced, exceeded, or otherwise behaved unexpectedly relative to the declared timeout.

If the discrepancy is reproduced, preserve it. If it is not reproduced, preserve both the historical evidence and the new result; do not erase the earlier observation.

## 12. Desktop 0.152 reviewer/wait anomaly policy

The prior Desktop 0.152 observation is treated as an unclassified compatibility anomaly: reviewer UI completed, while the parent wait path did not return within the observed period and was interrupted.

Plan F may run a narrow targeted acceptance to determine whether the behavior reproduces. Classification rules:

- child completion plus normal parent return: PASS for that acceptance run, while historical anomaly remains documented;
- child completion plus stalled parent wait: record the anomaly as reproduced;
- missing child lifecycle evidence: investigate separately; do not infer the wait anomaly is the cause;
- no result because the UI/runtime cannot be exercised: `BLOCKED`, not PASS.

No CEK-hook root-cause claim and no Codex-engine defect claim is allowed without direct evidence.

## 13. Interactive plugin discovery

Interactive plugin discovery is accepted separately from non-interactive plugin list/install behavior.

Do not infer an interactive command or UI contract from binary strings, current documentation alone, or a non-interactive CLI command. Record the actual surface used, runtime version, observed plugin identity, and whether the plugin can be discovered without modifying the user's normal profile.

If a declared baseline does not expose the same interactive surface, mark that row `BLOCKED` or scope the claim to the runtime where it was actually observed.

## 14. Public documentation migration

### README

README becomes the primary user-facing v0.2 status page. It must:

- remove stale statements that the project exposes only six active skills;
- describe the current eight-skill surface without implying broad domain expertise beyond the tested skill contracts;
- distinguish native plugin packaging, hooks, subagents, verification/evals, manual worktree acceptance, and optional domain packs;
- state the tested runtime window only as supported by the compatibility matrix;
- include an `implemented / verified / limited / planned` capability table or an equivalent evidence-bound structure;
- remove `lean` as a measured capability until the real complete benchmark exists;
- avoid `production-grade`, blanket `secure`, feature-parity, and unqualified cross-platform claims;
- state Python runtime requirements for hook/runtime-dependent features and distinguish them from skill-only use;
- link directly to compatibility, claim-evidence, benchmark, security, and release-checklist documents.

### SECURITY

SECURITY must reflect v0.2 boundaries:

- hooks are guardrails, not a sandbox;
- non-managed hooks require trust review unless a vetted one-off acceptance intentionally bypasses trust;
- local `.codex-kit/` state remains bounded and secret-sensitive;
- Python availability is a v0.2 limitation for hook/runtime-dependent features;
- learned candidates remain review-gated;
- acceptance evidence must not commit tokens, raw private transcripts, or auth/session material.

No blanket security guarantee is introduced.

### ROADMAP

ROADMAP must stop describing v0.2 merely as cross-platform installer parity. It should reflect the actual v0.2 native plugin, hooks, subagents/state, verification/evals, worktree/domain/benchmark, and release-evidence slices. Future items must be separated from shipped v0.2 capability.

### THIRD_PARTY_NOTICES

THIRD_PARTY_NOTICES keeps independent-implementation attribution and MIT upstream notice. It must not describe v0.2 as merely renaming or emulating Claude-specific lifecycle behavior. Native Codex hook/subagent/plugin implementation should be distinguished from high-level workflow inspiration. No endorsement claim is added.

## 15. Deterministic release contracts

Plan F adds deterministic tests before changing public release wording.

The release contract should reject at least:

- stale public statements that only six skills are active;
- measured `lean` wording without a linked real benchmark artifact;
- unsupported `production-grade`, feature-parity, blanket `secure`, or unqualified cross-platform wording;
- a compatibility row marked PASS without an evidence reference;
- release documents missing the 0.147.0 and 0.152.0 baselines;
- release readiness marked closed while required compatibility or claim-evidence rows are unresolved;
- machine-local paths, secret-like values, raw session identifiers, and placeholder text in release artifacts.

Static tests do not prove runtime compatibility. They prove that documentation and evidence metadata obey the release contract.

## 16. Acceptance helper design

Runtime acceptance helpers must be deterministic around process handling and conservative around conclusions.

Requirements:

- exact runtime binary is an explicit input for acceptance runs;
- no fallback to an arbitrary global Codex binary when a baseline path is required;
- disposable acceptance state is used instead of the user's normal Codex profile wherever supported;
- command timeout/nonzero/invalid output becomes FAIL or BLOCKED according to the documented case, never fabricated PASS;
- raw captures are bounded/sanitized before commit;
- acceptance artifacts include the tested repository commit SHA;
- helpers do not rewrite the primary plugin manifest for RISK-001;
- helper unit tests use deterministic fixtures/mocks where appropriate; authenticated/runtime execution stays outside ordinary CI.

## 17. Release-candidate gate

The v0.2 RC checklist may close only when all required release conditions are satisfied on one exact branch head.

Required conditions include:

- fresh repository CI is green on the RC head;
- Plan A-E closure evidence remains reachable from that head;
- compatibility matrix is complete for all required surfaces on both declared baselines, with PASS/FAIL/BLOCKED/NOT_RUN recorded honestly;
- every promoted public claim has a claim-evidence row;
- primary plugin manifest and marketplace contracts remain valid;
- RISK-001 experiment result is recorded even if RISK-001 remains open;
- RISK-002 differences are documented and do not exceed the scope of public compatibility wording;
- SessionEnd discrepancy is explicitly represented as resolved or still limited;
- Desktop parent-wait anomaly is represented according to the latest targeted evidence;
- README/SECURITY/ROADMAP/THIRD_PARTY_NOTICES pass deterministic release contracts;
- repository secret/content scans pass;
- no measured `lean` claim exists without a real complete 45-run campaign;
- no `main` merge is performed as part of checklist closure.

A release can be evidence-bound while some non-core risks remain documented limitations. A core capability failure on a declared baseline must narrow the release claim or block the RC.

## 18. Failure handling

Plan F preserves negative evidence.

- Acceptance failure: record FAIL with bounded evidence and stop claim promotion.
- Environment unavailable: record BLOCKED; do not infer behavior.
- Runtime version mismatch: invalidate that acceptance attempt for the targeted baseline.
- Dirty or unexpected primary repository state: stop the write/acceptance step until provenance is understood.
- Secret/private material in capture: keep raw material out of the repository and commit only sanitized evidence plus a hash when allowed by existing policy.
- Current official docs disagree with the declared baseline: record both; runtime acceptance determines what the project can claim for that baseline.
- CI regression after docs/evidence changes: Plan F remains open until fixed and reverified on a fresh run.

## 19. Testing strategy

Implementation follows RED -> verified RED -> minimal GREEN -> focused regression -> fresh CI.

Testing layers:

1. release-document static contracts;
2. compatibility/acceptance helper unit contracts;
3. existing Plan A-E regression suites;
4. real Codex CLI 0.147.0 acceptance;
5. real Desktop bundled 0.152.0 acceptance;
6. final claim-to-evidence audit and fresh CI on the exact closure head.

Authenticated or interactive runtime acceptance is never replaced by synthetic CI fixtures. Synthetic fixtures test the harness, not Codex behavior.

## 20. Implementation sequencing constraint

The later implementation plan should preserve this dependency order:

1. release evidence schema and RED static contracts;
2. compatibility/acceptance helper contracts;
3. RISK-001 disposable explicit-manifest experiment support;
4. baseline-specific 0.147.0 and 0.152.0 acceptance/evidence;
5. claim-to-evidence and compatibility matrices;
6. public documentation migration;
7. RC checklist and final regression/CI gate.

Public docs must not be promoted ahead of the evidence rows they depend on.

## 21. Completion boundary

Plan F is complete when the repository has an evidence-bound v0.2 release surface and the RC checklist can be evaluated from concrete artifacts on one exact commit.

Plan F completion does not itself mean:

- `main` has been merged;
- a public release has been published;
- the 45-run benchmark has been executed;
- `lean` has been measured;
- all future Codex versions are compatible;
- the project is production-grade or secure as blanket properties.

Those claims require their own evidence and explicit release action.
