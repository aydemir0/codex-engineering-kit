# v0.2 Verification Engine and Executable Evals Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the Windows-only verification core with a cross-platform Python verification engine, add deterministic package-manager resolution and executable offline evals, and provide a safe authenticated `codex exec` pressure-acceptance path.

**Architecture:** Keep command execution, package-manager resolution, project-specific verification, report serialization, eval grading, and authenticated Codex execution as separate stdlib-only modules. `scripts/verify.ps1` becomes a compatibility wrapper around the Python engine. Offline evals grade structured JSON candidates deterministically; authenticated pressure runs ask Codex for the same structured contract and never rely on a model grader when a code grader can decide the result.

**Tech Stack:** Python 3.11 standard library, JSON, TOML via `tomllib`, PowerShell compatibility wrapper, Node 22 for fixture execution, GitHub Actions on Ubuntu/Windows/macOS, OpenAI Codex `exec` only for operator-assisted authenticated acceptance.

**Spec:** `docs/superpowers/specs/2026-09-03-codex-native-plugin-v0.2-final-design-v2.md`

## Global Constraints

- Core verification/eval runtime uses Python 3.11 standard library only.
- Verification project types: Node/TypeScript, Python, and generic repositories.
- Every verification step records command, exit code, duration, and exactly one status from `passed`, `failed`, `skipped`, `unavailable`.
- A `skipped` step is never rewritten or summarized as `passed`.
- Node manager resolution order is: explicit invocation setting, `packageManager`, lockfile, available non-npm manager, npm fallback only when a `package.json` exists and npm is available.
- Initial Node managers are exactly `npm`, `pnpm`, `yarn`, `bun`.
- An authoritative `packageManager` or lockfile selection that is not installed becomes `unavailable`; it does not silently fall through to another manager.
- Multiple conflicting manager lockfiles without a `packageManager` field are reported as ambiguous and do not trigger a guessed manager.
- Commands execute with `shell=False` except the narrow Windows `.cmd`/`.bat` compatibility path, which uses the resolved `COMSPEC` and `subprocess.list2cmdline`.
- Captured stdout/stderr is bounded to the final 8 KiB per stream in artifacts.
- Verification/eval artifacts live under gitignored `.codex-kit/`; no raw private transcript, API key, OAuth token, or user-local credential is persisted.
- Documentation must warn that discovered build/test/lint/typecheck scripts are project-authored code executed with the current Codex/user permissions.
- Offline eval classes are capability, regression, and pressure.
- Pressure inventory is exactly: unsupported performance claim, unbounded concurrency, destructive shell shortcut, skip-tests-and-ship, secret-in-repository.
- Authenticated pressure runs require a discovered read-only sandbox option from `codex exec --help`; if unavailable, the runner reports `unavailable` and does not invoke the case.
- Authenticated runs are not CI requirements and are never faked by standalone dispatcher calls.
- No reliability metric such as `pass@k` or `pass^k` is emitted unless the matching number of real attempts was executed.
- Existing RISK-001/RISK-002 and the Codex 0.147.0 SessionEnd timeout discrepancy remain outside Plan D.

- [ ] **Step 2: Define exact deterministic pressure expectations**
